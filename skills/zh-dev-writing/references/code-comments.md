# 代码注释风格

与具体项目和编程语言无关的通用规约.

## 原则

注释承担两件事, 两件事的判断标准完全不同, 混在一起谈就会写歪:

- **What** —— 一句话说明"这是什么", 让读者不必读实现, 就知道要不要往下看.
- **Why** —— 说明代码为什么长成这样, 补上代码本身表达不出来的那部分.

What 让代码好读, Why 让代码改得动. 两者都不值得写的地方, 就一行注释也不要写.

## 一、What 写在哪里

判断标准只有一条: **读者会不会把这段代码当作一个整体来使用, 而不是逐行读它.** 会, 就值得给它一句 What.

该写的:

- 文件或模块的开头, 说明它负责什么.
- 对外暴露的函数、类、类型, 尤其是名字说不清行为的那些 —— 名字说得出"做什么", 说不出"返回什么形状"、"什么条件下返回空"、"有没有副作用".
- 数据结构的字段. 字段名通常只有一两个词, 一句 What 能省去读者搜索"这个字段由谁写入"的工夫.
- 长文件里的分区. 一行分隔注释把几百行切成几块, 比任何目录都管用.
- 一眼看不出意图的常量与配置项.

不该写的:

- 只在文件内部使用、名字已经把事情说清楚的小工具函数. 一个叫 `isWhitespace` 的三行函数, 不需要注释再告诉你它判断空白.
- 局部变量. 名字不够清楚就改名字, 不要用注释打补丁.
- 一望而知的赋值、分支、循环.

这条界线的意义在于, 注释的价值是相对的: 满屏都是注释时, 真正重要的那几条反而被淹没; 只在读者会停下来看的地方写一句, 那一句才有人读.

## 二、Why 写在哪里

Why 的判断标准是: **这段代码为什么写成这样, 从代码本身能不能读出来.** 读不出来, 才需要注释来补.

典型场合:

- **数据结构与持久化格式的决策.** 字段为什么可空, 取值范围为什么排除了某个值, 两个看似能合并的字段为什么分开.
- **迁就外部行为的写法.** 第三方库的类型声明不准, 接口返回的形状与文档不符, 语言本身存在语法陷阱. 这类代码单看像是随手写的, 不写清楚就会被"顺手修正"回去.
- **不可逆的约束.** 改动会让已经落盘的数据失效, 会破坏兼容性, 或者必须连同测试基准一起更新.
- **看起来能简化、实际不能的代码.** 注释要说清简化之后会坏在哪里, 否则下一个人一定会替你简化掉.
- **有意为之的不完整.** 出错后继续执行而不是中断, 静默降级, 保留一个看似多余的分支 —— 说明为什么这是正确的选择.

一段复杂但直白的算法, 可以完全不写 Why; 一行不起眼的 `if`, 如果拦下的是一个隐蔽的边界情况, 就该写.

## 三、篇幅

What 一行写完. 一行写不完, 多半是名字起得不好, 先改名字.

Why 可以长, 长度取决于要说清多少后果, 但每一句都得有信息量.

两者同时需要时, 先一句 What, 空一行, 再写 Why:

```
/**
 * 把源码归一化成用于比对的文本形式.
 *
 * 变更检测完全依赖这个结果: 注释增删与重新缩进不算实现变更, 归一化把它们抹平, 否则一次
 * 全仓格式化会把所有记录标记为过期. 字符串字面量原样保留, 其内容属于实现的一部分.
 */
```

## 四、Why 要落到具体后果

好的理由都经得起核对: 别人能顺着它推断出改动的后果. 常用的句式有四种:

- **否则会怎样**: "否则一次格式化会把所有记录标记为过期."
- **换一种写法会怎样**: "若以'有名字的节点就是类型'为准, 会一路吞掉上一条声明的整个函数体."
- **为什么不选那个更显然的方案**: "改成嵌套结构后, 读取单个成员需要反序列化整棵树."
- **改动的代价**: "任何改动都会让已存的全部指纹失效, 需要连同基准用例一起评估."

反面典型是"为了性能"、"为了安全"、"历史原因"、"这里比较特殊"这类表述: 读起来像理由, 却给不出任何可供核对的内容, 下一个人读完照样不敢改.

## 五、语体

写说明文, 不写口语旁白. 用陈述句, 主语用具体名词, 不用代词.

- 不写: "客户端把它读到的时间戳带回来, 对不上就不让写."
- 应写: "乐观并发控制: 客户端提交它读取时的版本号, 与服务端当前值不符则拒绝写入."

"把它 / 靠它 / 拿它 / 挡住 / 坑 / 搞 / 塞进去"这类口语措辞要避免 —— 它们把读者的注意力引向说话的语气, 而不是信息本身.

比喻只在中文里有现成说法时偶尔使用; 不要自造比喻词反复使用, 否则后来的人会误以为那是项目里的正式概念.

不写情绪化的表述和免责的话: "这里有点绕"、"暂时这么写"、"不知道为什么但能跑", 这类话不提供任何信息. 确实不确定的, 就写清楚不确定的是什么、什么条件下需要重新审视.

## 六、格式

- 注释单独占行, 放在被说明对象的正上方. **不写行尾注释** —— 格式化工具一换行, 它的位置就会漂移, 而且行尾空间有限, 写不下一句完整的话.
- 只有一句话的注释也要写成文档注释 (多数语言里是 `/** ... */` 或 `"""..."""` 这类编辑器能识别的形式), 悬停即可看到, 不必跳转到定义.
- 文件级说明写两件事: 这个文件负责什么, 整体结构为什么这么定. 不要罗列文件里有哪些函数 —— 那份清单迟早过时.
- 参数说明只写参数名推不出来的信息; 只有一两个参数需要解释, 就只写这一两个, 不必凑齐.
- 注释语言和标点风格在一个项目内必须统一. 中文注释里往往夹着大量英文标识符和代码片段, 全角标点会让间距忽宽忽窄, 因此建议统一用半角标点; 但无论选哪一种, 混用全角和半角都比始终只用其中一种要糟.
- 标识符、类型名、断言消息保持原文, 不翻译.

## 七、不要写的东西

- **复述代码的字面意思.** 循环上面写"遍历列表", 纯属噪声.
- **引用文档章节号.** 读代码的人手上未必有那份文档, 编号也迟早会变; 把理由本身写进注释里.
- **过时的经历叙述.** "以前用的是 A, 后来改成了 B" 该由版本历史来记录. 只有当"改回 A"的提议反复出现时, 才值得在注释里写明"为什么不能改回 A".
- **注释掉的代码.** 直接删, 需要时从版本历史里取回.
- **为凑覆盖率生成的模板文档.** 一堆 "@param x the x" 只会稀释真正重要的那几条注释.

## 八、落笔前的自检

1. 我要写的是 What, 还是 Why?
2. 是 What: 读者靠这一句, 能不能省下读实现的时间? 省不下 —— 比如一个三行的私有辅助函数 —— 就不要写.
3. 是 Why: 这个信息代码里看得出来吗? 看得出来就不要写.
4. 如果一段代码要靠很长的注释才解释得清, 先考虑改代码: 换个函数名、把中间步骤提取成命名清晰的变量, 往往能省掉一半注释.

## 九、改写示例

**复述代码 → 删掉**

```
- // 遍历所有订单并累加金额
  for (const order of orders) { total += order.amount; }
```

**私有小函数 → 不写; 对外函数 → 一句 What**

```
- /** 判断字符是否为空白字符. */
  function isWhitespace(ch) { ... }

+ /** 解析单个源文件, 语法错误不中断解析, 记入 diagnostics 后继续处理其余部分. */
  export function parseFile(path, source) { ... }
```

**口语旁白 → 说明文**

```
- /** 客户端把它读到的时间戳带回来, 对不上就不让写. */
+ /** 乐观并发控制: 客户端提交读取时的版本号, 与服务端当前值不符则拒绝写入. 首次写入为 null. */
```

**章节号引用 → 把理由本身写出来**

```
- /** 取值范围见设计文档 §5.2, 不含 auto. */
+ /**
+  * 状态列的取值范围.
+  *
+  * 不含 auto: 这个来源由后台任务整体重建, 写进人工编辑表会被下一轮任务覆盖.
+  */
```

**抽象理由 → 具体后果**

```
- // 为了性能, 这里复用实例.
+ // 解析器与查询对象的构造开销显著, 而单文件解析位于热路径, 故在进程内复用.
```

**小字段配长篇 → 压成一句**

```
- /**
-  * 起始行号.
-  *
-  * 这里用 1 起算是因为编辑器和大多数工具都从 1 开始计数, 如果从 0 起算, 展示时
-  * 还要再转换一次, 容易出错, 所以统一在这里就用 1 起算.
-  */
+ /** 从 1 起算. 起点含注解与文档注释, 便于按行截取完整声明. */
```

**看似能简化的代码 → 说清简化后坏在哪**

```
+ // 前一个字符属于标识符时, 这个 r 是标识符的一部分, 不是原始字符串的前缀.
  if (ch === 'r' && (i === 0 || !isIdentChar(src[i - 1]))) { ... }
```
